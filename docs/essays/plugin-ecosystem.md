# 宿主—内部插件—社区插件三层生态论证

> 本文论证 dsc 插件体系为什么按「宿主、内部插件、社区插件」三层组织,它为什么可行,以及它对开发者与用户的现实意义。
> 论证按「是什么—为什么—怎么办」展开;事实性表述均落到具体仓库文件,只依据各仓库 README、docs/design/ 与 specs/ 的既有结论。
> 本文不引入新设计,不承诺任何未定稿项;同目录另有 trust-system.md(信任体系)与 asset-ecosystem.md(资产生态)。
> 本文口径与各仓库文档冲突时,以各仓库文档为准。

## 一、是什么

三层生态按「谁做的、谁背书、怎么分发」划分,每层职责清晰:

| 层 | 承担者 | 代表仓库 | 职责 |
|:---:|:---:|:---:|:---:|
| 宿主 | 主线仓库本体 | DeepSeek-Chat-Enhanced | 提供聊天基本服务(dsc-core)、插件引擎(dsc-plugin-engine)与插件市场(dsc-market),不进入插件列表 |
| 内部插件 | 从宿主本体解耦出来的可选插件,组织自研维护 | dsc-inner-plugin | 把不必需的能力从本体拆出,单独安装、单独停用,整站由 dsc 签名发布 |
| 社区插件 | 第三方开发者投稿 | awesome-dsc-plugin | 社区精选合集,按分发规范收录、用合集 EEC 重签并分发 |

依据:DeepSeek-Chat-Enhanced:README.md「内置了以下基础插件」表与「插件市场」节。
依据:dsc-inner-plugin:README.md「定位」「与 awesome-dsc-plugin 的结构差异」节。
依据:awesome-dsc-plugin:README.md「定位与收录范围」节。

宿主借用了「Everything is a Plugin.」的理念,引入插件体系并制定统一规范;
所有插件由 dsc-plugin-engine 负责引入,通过引擎提供的标准接口有限地控制页面;
绕过引擎直接交互 dsc-core 的行为会被引擎识别并报出警报给用户。
依据:DeepSeek-Chat-Enhanced:README.md 开头与「制作插件」节。

## 二、为什么

### 2.1 宿主不可能内置所有需求

- 宿主的本职是一个静态聊天网页,它满足的是最大公约数的需求。
- 需求是长尾的:界面偏好、参数调节、供应端点切换、人性化定制,每个用户的组合都不同。
- 全部内置会让本体膨胀且不可停用;全部外放又没有组织背书的底线。
- 所以本体只保留三个基础模块(核心、引擎、市场),其余能力全部解耦为可安装、可停用的插件。
- 「每个 dsc 插件在开发阶段都是独立项目、运行阶段是一个符合产物规范的 js 脚本」,解耦从规范上就是一等公民。

依据:DeepSeek-Chat-Enhanced:README.md「制作插件」节。
依据:.github:profile/README.md「仓库矩阵」表。

### 2.2 内部插件保证底线质量与纯前端承诺

- 内部插件的收录条件直接写入组织承诺:承诺不采集、不外传用户凭证与数据,不自行发起任何网络请求,不读取与插件功能无关的会话内容。
- 这条承诺有机检兜底:收录与发布前对每个版本的 plugin.js 做静态扫描,命中全局 fetch、XMLHttpRequest、WebSocket、EventSource、sendBeacon、远程动态导入即报 PLUGIN_NETWORK_SELFTALK。
- 产物必须是单个浏览器 ESM 脚本,不依赖 Node 内置模块与后端接口;不收录需要后端服务、需要原生模块、或无法在 CI 中重建产物的插件。
- 「内部插件本身可信,但仍要走市场普通安装通道」,没有免检的快捷通道:可信不等于免检。
- 这一层是纯前端承诺的执行边界:用户可以从组织来源安装,而不必担心凭证外传成为默认行为。

依据:dsc-inner-plugin:README.md「收录条件」「产物静态扫描」「软安全门禁」节。

### 2.3 社区插件保证丰富度

- 组织自研永远覆盖不了长尾;社区投稿是丰富度的唯一来源。
- 社区合集的收录条件把「能不能进」写成一组可机检的事实:产物形态、元数据完整、npm 包已发布且与插件名一致、CI 能按 base_url 拉取并复核产物。
- 收录不等于认证:合集只保证分发内容与签名一致,不审查插件行为;主线安全提示同样明确「由 awesome-dsc-plugin 收录的插件可能存在审查遗漏」。
- 这条诚实边界让丰富度与风险提示并存:用户获得更多选择,同时被明确告知自行判断。

依据:awesome-dsc-plugin:README.md「定位与收录范围」。
依据:DeepSeek-Chat-Enhanced:README.md 提示区。

### 2.4 npm 包名一致降低用户侧决策成本

- 收录硬条件:插件必须先发布到 npm,且 npm 包名与插件名一致——dsc-xxx 对应 npm 包 dsc-xxx,带 scope 的同理。
- 仓库级校验、PR 预检作业与 Release CI 都会查询 npm registry;包不存在或登记包名与插件名不一致都以错误拦截,PR 与 CI 双重拦截,没有发布就不会被收录。
- 对用户的含义是:看到插件名就能找到它的 npm 页面、源码仓库与安装来源,不用在多个同名产物之间猜。
- 一个名字贯通登记、分发与溯源,决策成本从「核对多个渠道」降到「记住一个名字」。

依据:awesome-dsc-plugin:README.md「定位与收录范围」与 scripts/lib/npm-package-check.mjs 说明。

## 三、怎么办:为什么可行

### 3.1 能力与挂载点契约

- 插件对宿主的一切访问只走 context 上的受限能力对象,能力清单封闭且逐项限流,完整清单见运行时规范第四节,第三方可申请的能力与内置专用的能力分表列明。
- net:fetch 只对内置插件开放:第三方插件在清单里申请它,按 unknown-capability 拒绝,调用层再校验一次。
- 插件拿不到 API Key、附件原件、请求快照与其他插件的本地数据;可见数据范围逐项列明。
- 挂载点同样封闭:只有清单声明了对应能力才能订阅,安装时按清单校验能力与挂载点,名字不在表内即拒绝(unknown-mount),调用时再校验一次。
- 引擎持有调用凭证,每次调用签发一次性票据,绕过 context 直接调用核心会被拒并记录旁路事件。

依据:dsc-plugin-template:specs/plugin-runtime-spec.md 第四节「能力与限流」、5.1、5.2、6「安全边界」。

### 3.2 安装校验

- 安装的两条入口共用一条清单规则:「从地址安装」由产物自带的 manifest 导出提供清单;「从本地安装」的离线包由 meta.json 推导清单,两者都由引擎在安装阶段补齐挂载点。
- 在线来源的校验顺序固定:先用内嵌根证书校验合集证书链,链通过才做 CMS 验签;链不通过直接给失败结论,不再验签。
- 产物由 plugin.js.sig 单独验证,作者签名作为可选材料并存;签名结论三态(通过、未校验、失败)与来源结论四态(已确认、未确认、校验未通过、本地安装)两条轴互不替代。
- 校验不通过时只给出警告,不阻止安装或使用,由用户自行判断是否继续。

依据:DeepSeek-Chat-Enhanced:README.md「插件面板」节。
依据:DeepSeek-Chat-Enhanced:docs/design/trust-and-signature.md 第三、四、五节。
依据:DeepSeek-Chat-Enhanced:src/components/dsc-market/README.md「meta.json 与安装清单」节。

### 3.3 互斥与依赖治理

- 插件声明宿主版本依赖:meta.json 的 dependencies.dsc 映射为清单的 engines 字段。
- 互斥由清单 conflicts 声明,在安装阶段判定:dsc-humanize 与 dsc-llm-tune 都改写请求参数,两侧清单互相声明 conflicts,同时安装即拒绝;只改一侧等于没有互斥。
- 多个插件同时登记同一挂载点时,由引擎按登记顺序合并,标量以后登记者为准,并集与拼接按上限收敛。
- 这些治理让「装了很多插件」不会变成「参数互相打架」:冲突在安装时挡住,共存时的合并顺序确定可解释。

依据:DeepSeek-Chat-Enhanced:src/components/dsc-market/README.md「meta.json 与安装清单」节。
依据:dsc-humanize:docs/design/kernel-and-assets.md 4.3(与 dsc-llm-tune 的互斥)。

### 3.4 市场渠道已有实现

- dsc-market 是宿主内置插件,负责按来源拉取插件目录、校验来源信任链、组装安装计划并上报下载计数,由插件引擎装载。
- 来源模型:一个来源由名称与一组 base_url 组成,按顺序尝试,单请求短超时,失败自动切下一个;内置 dsc-inner-plugin 与 awesome-dsc-plugin 两个来源,用户可自建来源。
- 取件与校验按固定顺序执行:meta.json、信任清单登记、来源证书三档取件、目录数据模型识别(合集模型或整站模型)、逐层清单验签、版本与产物取件。
- 更新检查读 versions.json 的 latest;旧版本安装记录可用「重新安装」按同一流程补全校验;已移除插件清单让「安装失败」能区分「已下架」与「不存在」。
- 资产市场在 dsc-humanize 设计文档中明确以它为形态参照,但两者不共享来源列表、不共享信任锚。

### 3.5 开发者有清晰的上架路径

- 第一步:用 dsc-plugin-template 模板起步,按产物规范与开发规范写插件。
- 第二步:发布到 npm,包名与插件名一致。
- 第三步:向 awesome-dsc-plugin 提交收录 PR,提交 author.json、author_pub.pem 与 plugin.json 三个文件即可完成登记,不需要改脚本。
- 第四步:CI 按登记从作者自己的 base_url 拉取产物,用合集 EEC 重新签名,组装 pages 包并发布;作者站点仍是版本的第一来源,合集只做收录与重签。
- 每一步的条件与失败原因都写在文档里:登记不合规中止构建,运行期异常只剔除该插件,签名与扫描命中只警告。

依据:awesome-dsc-plugin:README.md「收录流程」「如何收录插件」节。
依据:DeepSeek-Chat-Enhanced:README.md「制作插件」节。

## 四、现实意义

### 4.1 对开发者:一条明确的路

- 从模板到收录,路径只有四步,没有私聊、没有特批、没有隐藏门槛。
- 收录判定全部可机检、可预检:提 PR 前就能用同一份预检脚本自查。
- 作者身份有自己的表达空间:作者签名与合集签名并存,文件名区分签名者;作者站点仍是版本源头,合集不占有产物。
- 收录不等于认证的边界同样保护开发者:合集不为任何人的行为背书,责任与荣誉都归到作者自己。

依据:awesome-dsc-plugin:README.md「如何收录插件」「作者自签名」节。

### 4.2 对用户:统一的安装体验

- 一处管理:插件面板的「已安装」列出名称、版本、状态与来源,可启用、停用、卸载并查看日志。
- 一处发现:「插件市场」读取来源索引直接安装,可刷新、可换源、可自建来源。
- 一致的提示口径:签名结论与来源结论各管一条轴,「未校验」不说成「失败」,「无法判定」不说成「地址无效」。
- 一致的更新与回退:可更新提示、重新安装计划、已下架清单,都是同一条链路上的动作。

依据:DeepSeek-Chat-Enhanced:README.md「插件面板」节。
依据:DeepSeek-Chat-Enhanced:src/components/dsc-market/README.md「版本更新检查」「缓存与失败处理」节。

### 4.3 机制上的三段式:核心引领、周边共建、激发参与

- 核心引领:宿主与引擎立规范,基础模块划底线,能力契约决定「能做什么」。
- 周边共建:内部插件守承诺,社区合集供丰富度,合集 CI 统一签名与分发。
- 激发体验与自发参与:插件侧用户得体验——装上即用、可停用、可更新;开发者做贡献——有模板、有规范、有市场,作品的触达不依赖自己建站推广。
- 三层各司其职,互不越位:宿主不替用户挑内容,合集不替作者背书,市场不替用户做信任决定。

依据:.github:profile/README.md「生态与角色」「组织原则」节。

## 五、为什么值得:开源软件的普惠路径

开源软件从边缘走到今天的位置,靠的不是某一项技术发明,而是一条低门槛的参与路径:
一份规范、一个模板仓库、一条 PR 流程,就能让陌生人的代码被陌生人安全地使用。
Linux 发行版的仓库体系、各语言包管理器的注册表,本质上都在做同一件事——
把「发布、发现、安装、校验」四件事标准化,让贡献者不必重复造分发轮子,让用户不必逐一审源码。

dsc 插件三层生态走的是同一条路径:
宿主立规范,合集管分发,市场管发现,签名管校验。
它把「给 DeepSeek 增加一个功能」的成本,从「读懂并魔改整个网页」降到「照模板写一个脚本再提一个 PR」。
功能被更多人复用的同时,每一次安装都带着可核验的出身——
普惠不是把东西堆给用户,而是让用户能放心地拿。
