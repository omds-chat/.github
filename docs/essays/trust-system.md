# CA-EEC-Sign 信任体系论证

> 本文论证 omds-chat 组织为什么需要一套自建信任体系、它为什么可行、以及它对用户的现实意义。
> 论证按「是什么—为什么—怎么办」展开;事实性表述均落到具体仓库文件,只依据各仓库 README 与 docs/design/ 的既有结论。
> 本文不引入新设计,不重复各仓库文档的技术细则;同目录另有 plugin-ecosystem.md(插件生态)与 asset-ecosystem.md(资产生态)。
> 本文口径与各仓库文档冲突时,以各仓库文档为准。

## 一、是什么

CA-EEC-Sign 是本组织信任体系的代称。
它用 X.509 证书链回答「签名者有没有资格」,
用 CMS 分离签名回答「这份字节是不是它签的」,
再用三层哈希清单与作者裸签名,补齐「目录数据」与「作者意愿」两级证据。
体系由三类角色构成,各持一把密钥:

| 角色 | 承担者 | 持有物 | 签发对象 |
|:---:|:---:|:---:|:---:|
| 根 CA | DeepSeek-Chat-Enhanced 仓库(ds-chat 根)与 dsc-humanize 仓库(资产根),私钥离线保管 | 根证书 | 各合集的终端签名证书(EEC) |
| 终端签名方(EEC) | 各插件与资产合集仓库 | EEC 私钥,存 CI secrets | 三层哈希清单与产物或包文件的 CMS 分离签名 |
| 独立签名方(作者) | 插件作者 | Ed25519 密钥对 | 插件产物的裸公钥分离签名,可选 |

依据:awesome-dsc-plugin:README.md「签名与校验」节。
依据:dsc-inner-plugin:README.md「签名与信任」节。

组织维护两棵互不隶属的信任树。

- ds-chat 根的下游:网页签名方、dsc-inner-plugin 与 awesome-dsc-plugin 两个插件来源的 EEC。
- dsc-humanize 根的下游:dsc-humanize-inner-asset 与 awesome-dsc-humanize-asset 两个资产合集的 EEC。
- 两个根都自签,都是 CA:TRUE 且 pathlen:0,只能签发末端证书;末端证书均为 CA:FALSE,密钥用途只有数字签名。
- 作者身份不出证书,用公钥直接验签,不在任何一棵树里。

依据:.github:public/certs/README.md「证书体系列表」「信任层级」「作者身份」节。

## 二、为什么

### 2.1 纯前端形态决定信任不能靠后端

- 本组织的产品形态是「纯前端静态页面、无后端、插件化扩展」。
- 官方源仓库本身就是一个基于 DeepSeek API 的静态聊天示例:无需应用后端,浏览器直接请求配置的 API 服务。
- 组织也明确只提供静态网页与插件的制作、展示与分发,不提供任何付费服务、后端服务。
- 没有后端,就没有一个「服务端替你审过」的中间人可依赖;所有内容都从静态分发地址直抵浏览器。
- 于是「这份内容是谁发的、有没有被改过」只能在浏览器本地回答,信任体系必须建立在客户端可校验的材料上。

依据:.github:profile/README.md;依据:DeepSeek-Chat-Enhanced:README.md。

### 2.2 页面与插件无法自证发布者

- 一份静态字节本身不携带身份:任何人都可以把它搬到自己的地址上原样提供。
- 更关键的是「部分替换」:单独替换目录里的一个文件,或替换索引后再替换文件,浏览者毫无察觉。
- 网页侧的对策是「清单签名 + 每个文件各签一份」:先验清单签名,再按清单逐文件验签;清单只允许相对路径,否则清单可以把自己指向站外。
- 插件侧的对策是「三层目录清单 + 产物单独签名」:目录数据被改不会让产物验签失败,产物被改也不会让目录清单失配,两条独立结论互不顶替。

依据:DeepSeek-Chat-Enhanced:docs/design/trust-and-signature.md 第二、三节。

### 2.3 普通用户无法人工核验,也不该学 openssl

- 核验一张证书、验一条 CMS 签名,需要的是 openssl 命令行。
- 组织确实把只读校验命令写进了公开证书说明,供愿意动手的人核对;但这属于维护者与作者的操作。
- 对普通用户而言,要求「先学 openssl 再用聊天页面」等于把人挡在门外。
- 正确的分工是:把关由组织在分发链路上完成,用户面对的只是来源状态与一条警告。
- 信任状态在市场里只有四档——trusted、endorsed、untrusted、unverified——每档对应的界面行为是确定的,不需要用户理解证书链。

依据:.github:public/certs/README.md「如何校验一张证书」「如何校验一条链」节。
依据:DeepSeek-Chat-Enhanced:src/components/dsc-market/README.md「信任状态」节。

### 2.4 浏览器环境对凭证的威胁面

- 插件运行在浏览器里,与宿主同源、跑在页面主线程。
- API Key 直接保存在浏览器存储中,主线安全提示写得很直白:不要轻易启用未知来源、不受用户本人信任的任何插件,以防 API Key 与会话内容泄露。
- 组织主页的权利声明同样把「浏览器运行与凭证风险」列为专门条款。
- 这个威胁面没有后端可以兜底,唯一的缓解是让每个来源的身份可核验、让每份产物的完整性可校验。

依据:DeepSeek-Chat-Enhanced:README.md 提示区。
依据:.github:profile/NOTICE.md。

### 2.5 为什么必须由组织把关

- 既然「用户不该学 openssl」,把关就必然落到有人替用户做的事前审查与事后可追溯上。
- 组织维护根证书机构,为受信任的合集签发证书;合集再为收录的插件签名。
- 用户从合集拿到的产物,因此可以追溯到组织认可的发布方。
- 同时体系诚实划定边界:签名只证明来源未被篡改,不证明插件安全、无害或持续维护;收录不等于认证。
- 把关不是替用户做决定,而是把「谁发的、有没有被改」变成人人可读的一条状态。

依据:.github:profile/README.md「签名与信任」。
依据:awesome-dsc-plugin:README.md「收录不等于认证」。

## 三、怎么办:为什么可行

### 3.1 全部复用既有标准与生态

- 这套体系没有发明任何新密码学。
- 证书是标准 X.509,签名是标准 CMS 分离签名。
- 生成与验证用 openssl 一条命令完成:合集签名固定 openssl cms -sign -binary -md sha512 -outform DER -nocerts -noattr,验签固定 -inform DER。
- DER 是跨仓库统一格式:默认的 S/MIME 包装浏览器无法解析,而校验要在浏览器里做。
- 浏览器侧用 WebCrypto 校验证书链;根 CA 与 EEC 都选 ECDSA P-256,正是出于 WebCrypto 对 P-256 支持最广的考量,而 Ed25519 在这些下限版本中尚不可用。
- 作者签名用 Ed25519 裸公钥分离签名(openssl pkeyutl -sign -rawin),与证书链互不依赖。
- 脚本只调用 openssl 命令行,不实现任何密码学运算。

依据:awesome-dsc-plugin:README.md「证书链」「命令」节。
依据:dsc-inner-plugin:README.md「证书链」节。

### 3.2 两层根域:插件与资产各自成链

- 组织没有把所有内容挂在一棵树下,而是按「被验对象」分出两个信任域。
- ds-chat 根签发插件与网页侧的 EEC;dsc-humanize 根签发资产合集的 EEC。
- 两条链互不隶属:拿 dsc-humanize 的根去校验 ds-chat 名下的证书会失败,反之亦然。
- 理由:两个信任域的根、签发者与失效时间各不相干;更根本的是被验对象不同——资产是用户导入的纯数据,插件是可执行产物,准入条件本就不同。
- 借用一边的结论,等于让一次校验通过建立在另一套主体的判断上。

依据:.github:public/certs/README.md「信任层级」。
- 另一个常见问法:为什么不是一根根证书下挂子 CA、再由子 CA 签发末端?答案在这套体系的规模与运维现实里。
- 全组织需要签发末端证书的主体只有个位数,且全部由组织自己运营;子 CA 的价值在于把签发权下放给多个彼此独立的团队或期限更短的运维单元,我们根本没有这个下放需求。
- 引入子 CA 却要付出实打实的代价:链多一级,浏览器端校验多一次取件与验签;根的 pathlen:0 与两级直签让吊销语义保持最简——吊销一张 EEC 就是吊销一张 EEC,不会牵连它名下的下级;根私钥可以永远离线,不需要为了日常签发把任何中间私钥放在 CI 里。
- 两条根各自 pathlen:0、只签末端,是同一个取舍在两个域里的重复应用:让链短到用眼睛就能看完整,让每一个签发决定都留在组织的离线流程里。
- 子 CA 不是被否定,而是被留到它真正被需要的那天:当出现「组织之外的第三方合集运营方」需要自主签发时,给那一方签一张子 CA 证书才是正解;在那之前,扁平的两级链是复杂度最低的合规形态。
依据:dsc-humanize:docs/design/kernel-and-assets.md 2.10。

### 3.3 三层哈希清单

- 合集把目录数据分成三层,每层一份哈希清单与一份清单签名。
- L1 覆盖合集元数据、插件目录索引、标签词表与作者清单。
- L2 覆盖作者公钥与插件清单。
- L3 覆盖版本列表与各版本元数据。
- 三层互不引用,任何一层都可以单独发布、单独校验、单独重签。
- 取舍是放弃「一次校验拿到全树摘要」,换取按插件增量更新:改一个插件只需 L3 的 revision 加一,L1 与 L2 不动,客户端只重拉这一层。
- 若把三层收束成一份根清单,任何插件发版都会改动根清单,所有客户端都得重拉整份摘要。
- 产物本体不进清单,由每个版本的 plugin.js.sig 单独负责。

依据:awesome-dsc-plugin:README.md「分发结构」「三层之间不做收束」节。

### 3.4 作者签名是补充而非门槛

- 作者签名只覆盖 plugin.js 的原始字节。
- 它证明的只有一件事:插件代码与作者签署时一致。
- 它不能证明作者可信,不能证明展示信息没被改,也不能证明包里的其他文件没被改。
- 因此体系把它定位为可选材料:作者不签名、只给公钥或只给签名、验签不通过,都不阻断收录与安装,结论分别是未校验、未校验与失败。
- 公钥与签名两侧缺一不可:缺一判「未校验」,不把「没验过」写成「验过了」。
- 收录结论由合集侧的登记审核与仓库级校验决定,不因作者缺签名而拒绝产物。
- 这条边界背后是一组刻意保持的平衡。给作者签发证书,意味着作者要先向组织证明身份、组织要维护作者的身份册与吊销流程——信任建立的每一步都会变成贡献流程里的一个关卡;而社区贡献的门槛每高一分,愿意进来的人就少一层,这与资产生态「写几个 JSON 就能投稿」的低门槛取向直接冲突。
- 同时,证书给作者带来的增量信任近乎为零:合集 EEC 已经回答「这份产物由哪个合集认可并分发」,作者证书至多再回答「作者是谁」,而署名信息本来就在登记文件与 npm 包里公开可查。
- 保留的裸签名恰好补上证书不做的那一件事:作者无需向组织交出任何身份材料,也能在自己的密钥下留下「这份字节出自我手」的可验证痕迹;收录时公钥随登记入库,换库、换址之后来源仍可当场验明。
- 于是平衡落在:身份登记归合集(收录审核本来就要做),来源承诺归裸签名(可选、无门槛、不建信任册),组织信任归证书链(只发给合集,不给个人)。三层各答一个问题,谁也不替谁背书。

依据:DeepSeek-Chat-Enhanced:docs/design/trust-and-signature.md 3.3 与第六节。
依据:awesome-dsc-plugin:README.md「作者自签名」节。

### 3.5 失败只警告、不阻断

- 分发之后的校验是弱校验:链不通过、清单签名失败、逐文件失败,一律只提示不阻断。
- 浏览器里已经加载的脚本无法被「撤回」,阻断只会制造「页面坏了」的观感,不会恢复安全状态。
- 阻断会把用户推向不受管的分发方式(例如自行打包离线包),结果是既失去警示也失去记录。
- 「可见的不可信记录」比静默拒绝更有用:用户可以据此决定是否继续使用,也能事后追溯。
- 强校验留给发布侧:收录与发布前是强校验,任一规则不通过即中止,不合规的内容不会被分发。

依据:DeepSeek-Chat-Enhanced:docs/design/trust-and-signature.md 第五节。
依据:awesome-dsc-plugin:README.md「校验语义」节。

## 四、现实意义

### 4.1 发布可追溯

- 每份产物都能沿证书链回到组织根证书:网页产物回 ds-chat-pages,插件回对应合集 EEC,资产合集回 dsc-humanize 根。
- 根证书在构建时内嵌进产物:离线运行拉不到在线副本,内嵌的根证书是离线可用的前提。
- 出问题时能回答「这份字节当初出自哪个发布方」。

依据:DeepSeek-Chat-Enhanced:README.md「证书与信任数据」节。
依据:awesome-dsc-plugin:README.md 证书链图。

### 4.2 收录可审计

- 收录走 catalog 登记 PR,提交三个文件即完成登记:作者身份、作者公钥与插件登记。
- PR 触发预检作业,发布前跑仓库级校验与 pages 包强校验。
- 三层清单、清单签名、产物签名与收录信息交叉一致性都在这一步检查。
- CI 发布前再用 openssl 独立验签一遍,全部通过才替换已发布站点。
- 谁在什么时候收录了什么,全部落在可复查的登记与校验记录里。

依据:awesome-dsc-plugin:README.md「收录流程」「本地校验」节。

### 4.3 出事可撤回

- 根证书的密钥用途含 CRL 签发(cRLSign)。
- 启用吊销检查时,把根证书与 CRL 拼进同一个 -CAfile 并追加 -crl_check。
- 证书被吊销的结论随来源材料传入安装记录,记录标为不可信;吊销列表不可用时按未知处理,不据此误判。
- 除证书吊销外,合集可发布已下架清单 catalog/removed.json:用户取不到产物时,能区分「曾经有、后来下架」与「从来没有」。

依据:.github:public/certs/README.md「证书体系列表」。
依据:awesome-dsc-plugin:README.md「命令」节吊销检查说明。
依据:DeepSeek-Chat-Enhanced:docs/design/trust-and-signature.md 第五节。
依据:DeepSeek-Chat-Enhanced:src/components/dsc-market/README.md「已移除插件清单」节。

### 4.4 用户只面对「可信来源」一个开关

- 上面所有机制对用户的呈现收敛为一件事:来源是否可信、产物签名是否通过。
- 它以状态与一条警告表达;信任清单登记、证书链校验、CMS 验签都在幕后完成。
- 用户不需要理解任何细节,只需要在看到「不可信」标识与二次确认态时做出自己的判断。
- 市场不替用户静默放行,也不替用户拒绝;决定权始终在用户手里。

依据:DeepSeek-Chat-Enhanced:src/components/dsc-market/README.md「信任状态」节。

## 五、为什么值得:把可核验的出身留给每一份内容

亚历山大图书馆的散佚,不是因为内容不好。
是因为副本唯一、出处无凭——散佚之后,后人连「它曾经有什么」都无法回答。
非物质文化遗产的抢救是同一个教训的另一面:许多技艺失去后才发现需要,
而失去的根源,往往是它没有一个可被持续核验、再分发与传习的「正身」。
今天的数字内容复制成本趋近于零,但「出处」反而更易失散:
转载、改包、换地址之后,一份内容的出身几乎无从谈起。

CA-EEC-Sign 做的就是把「出身」固定在字节旁边。
每份产物都带着一条可以当场验明的链,散佚与冒名的风险被压到最低。
这直接服务于组织定位:本组织不是前沿探索者,
而是把前沿成果普惠到终端用户的助力者,推进「AI 普惠全人类」的最后一公里。
普惠的前提是可信;可信的形态,就是用户只面对「可信来源」一个开关。

依据:.github:profile/README.md。
