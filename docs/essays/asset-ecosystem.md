# 插件—内部资产—社区资产体系论证

> 本文论证 dsc-humanize 资产生态为什么按「插件、内部资产合集、社区资产合集」组织,它为什么可行,以及它对普通用户的现实意义。
> 论证按「是什么—为什么—怎么办」展开;事实性表述均落到具体仓库文件,只依据各仓库 README、docs/design/ 与 specs/ 的既有结论。
> 本文不引入新设计,不承诺任何未定稿项;同目录另有 trust-system.md(信任体系)与 plugin-ecosystem.md(插件生态)。
> 本文口径与各仓库文档冲突时,以各仓库文档为准。

## 一、是什么

### 1.1 插件承载逻辑,资产承载内容

- dsc-humanize 把「人性化」拆成两个正交的部分:内核决定怎么算,资产决定算成什么。
- 三方职责泾渭分明:内核做文本到标签、标签到策略、策略到注入片段;资产提供分类标签、策略库、提示词模板与人物设定;宿主决定策略是否落到请求参数与系统提示词上。
- 归类判据只有两条:是否含可执行逻辑(含归内核,不含归资产)、用户能否替换(内核不能,资产必须能)。
- 内核代码里不存在任何一句会进入系统提示词的文案;没有默认标签、默认策略、默认人设,变化的唯一来源是资产。
- 资产包与插件因此格式互不复用:插件清单承载能力申请与安装生命周期,这些概念在资产里没有对应物。

依据:dsc-humanize:docs/design/kernel-and-assets.md 2.1、2.2、2.4 节。
依据:dsc-humanize-asset-template:README.md「与插件的关系」节。

### 1.2 资产是四类纯 JSON

| 类型标识 | 名称 | 对应环节 | 承载什么 |
|:---:|:---:|:---:|:---:|
| persona | 人物设定 | 注入拼接 | 人设标识、展示名、拼在提示词前的固定前缀 |
| labels | 分类标签集 | 分类管线 | 标签标识、语义说明、关键词、权重 |
| strategies | 策略规则 | 策略解析 | 兜底策略、标签到请求参数的规则、合并顺序与阈值 |
| injection | 注入文本 | 注入拼接 | 可独立选择的文本片段 |

- 包由元数据 asset.json 与若干类内容组成;类型集合固定为四类,与流程环节挂钩。
- 声明是必填项,至少一类;只声明一类合法,四类齐全不是要求。
- 包内只有数据,没有代码:宿主不加载它,内核只读取它;不申请宿主能力,没有安装、激活这套生命周期。
- 资产包不做代码签名,包里也不放任何签名材料;完整性由分发渠道负责。

依据:dsc-humanize-asset-template:README.md「资产包是什么」「资产包不是什么」节。

### 1.3 两个合集加一个格式源头

| 仓库 | 身份 | 作用 |
|:---:|:---:|:---:|
| dsc-humanize | 内核插件,同时是资产侧根 CA | 定义内核与资产格式的边界,签发资产合集证书 |
| dsc-humanize-inner-asset | 内部资产合集(根 CA 签发的 EEC) | 收录组织自研的默认资产包 |
| awesome-dsc-humanize-asset | 社区资产合集(根 CA 签发的另一张 EEC) | 收录社区投稿的资产包 |
| dsc-humanize-asset-template | 格式定义方,不含资产 | 定义资产包格式、Schema、骨架、示例与校验脚本 |

依据:dsc-humanize-inner-asset:README.md「在资产生态里的位置」表。

## 二、为什么

### 2.1 内容的生产门槛必须远低于代码

- 插件承载逻辑,必须过工程关:ESM 产物、构建可复核、npm 发布、CI 拉取重签——这些门槛对逻辑类贡献是必要的。
- 内容不该付同样的门槛。一个人设、一套标签、一份注入文案,本质是「把想法写清楚」,不是「写一个程序」。
- 四类内容全是 JSON:复制骨架、改元数据、填内容、跑校验脚本,就是资产包的完整生产流程。
- 如果做一个人设要先学会构建工具与发布流程,内容生产者就被挡在了门外,生态只剩开发者。
- 所以体系刻意让资产与插件「不复用格式」:复用会把插件的版本牵制带进资产,把数据作者变成事实上的插件开发者。

依据:dsc-humanize-asset-template:README.md「怎么做一个资产包」「与插件的关系」节。
依据:dsc-humanize:docs/design/kernel-and-assets.md 2.2 节。

### 2.2 内部合集兜底,社区合集开放

- 内部合集收录组织自研的预设资产包,让用户开箱就有可导入的内容;它「是资产的来源之一,不是内核的一部分」,不带任何特权字段。
- 社区合集面向第三方投稿,收录条件写成四条可核对的事实:包本身合规、站点可访问、标识唯一、标签在词表内。
- 两个合集地位相同:都只由资产根签发的 EEC 证明身份,没有哪一条因为「内置」而跳过校验。
- 兜底与开放并存:兜底保证新用户第一天的体验,开放保证内容的长尾与多样性。

依据:dsc-humanize-inner-asset:README.md「定位」「收录条件」节。
依据:awesome-dsc-humanize-asset:README.md「定位与收录范围」节。
依据:dsc-humanize:docs/design/asset-market.md 2.2(两个内置来源地位相同)。

### 2.3 内核不内置内容,保证「预设只是来源」

- 插件不定义「好助手」的标准形象,也不内置任何性格;用户期望彼此冲突,任何默认形象都会对一部分用户变成静默偏差。
- 内置合集提供的是可导入的资产包,与用户自建包同格式、同校验;删掉内置合集不会减少任何能力,只会少几份现成内容。
- 用户不导入任何预设时,插件仍完整可用,只是不改变助手。

依据:dsc-humanize:docs/design/kernel-and-assets.md 1.2、1.3、2.6 节。

## 三、怎么办:为什么可行

### 3.1 格式 1.0.0 已定稿,源头唯一

- 规范版本与格式版本都是 1.0.0,登记在格式仓库的 specs/spec-version.json;包元数据的 formatVersion 用它。
- 权威文本是格式仓库的 specs/asset-package-spec.md;Schema 是同一份契约的机器表达,不一致时以规范文本为准。
- 规范与 Schema 只在这一处维护:其他仓库按 spec_version 选定版本并固定到具体提交,不在引用方另存一份规则。
- 社区合集明确不提供「复刻自身」的模板仓库,也没有第二份资产包规范;要改格式,回到格式仓库改并升版本,不在合集就地打补丁。
- 校验可执行:零依赖校验脚本只用 Node 内置模块,覆盖元数据 Schema、声明与内容双向一致、同类型标识唯一、标签引用自洽;判定是整包的,任何一项不通过整包不被接受。

依据:dsc-humanize-asset-template:README.md「规范与版本」「校验」节;依据:dsc-humanize-asset-template:specs/spec-version.json。
依据:awesome-dsc-humanize-asset:README.md「资产包格式只有一处源头」节。

### 3.2 两合集共用同一格式与同一信任域

- 两个合集用的是同一套包格式:版本目录就是资产包本身,内容与作者站点逐字节一致;合集不改写包内容。
- 信任域只有一条两级链:资产侧根 CA(CN=dsc-humanize ROOT CA)签发两个合集的 EEC;没有中间 CA,EEC 不能再签发。
- 信任锚只有一个:certs/dsc-humanize/dsc-humanize-root-ca.crt,锚在仓库里、由插件构建时内嵌,不从页面或索引临时取根。
- 这条链与 ds-chat 插件链互不隶属:资产根不参与插件签发,ds-chat 根不能验资产来源;两个信任域的根、签发者与失效时间各不相干。
- 与插件市场的关系也定死了:资产来源不进插件市场的列表;把资产来源挂进插件市场,会让一次插件生态的结论被当成资产来源的结论。

依据:awesome-dsc-humanize-asset:README.md「分发结构」「证书链」节。
依据:dsc-humanize-inner-asset:README.md「两级链」「锚点与校验」节。
依据:dsc-humanize:docs/design/kernel-and-assets.md 2.10;依据:dsc-humanize:docs/design/asset-market.md 1.2、3.2 节。

### 3.3 安装即导入,不覆盖任何已有选择

- 安装一个资产包 = 把包内容导入本地,并让它成为按类型组合的候选;它不覆盖任何已有内容。
- 每一类内容的来源由用户分别指定:某个包,或用户自己写;引入一个包不会顶掉用户在其他类型上的选择。
- 同类内容被两个包同时提供时,由用户选择其一或两者并用;内核不设跨包优先级,不提供「后导入覆盖先导入」。
- 包是只读来源:导入、组合、装配都不改写包文件;组合在内存副本上进行,结果落进当前使用快照。
- 安装是整包原子的:取件失败不落盘,整包校验失败不落盘,登记失败回滚——半套资产比没有资产更糟。

依据:dsc-humanize:docs/design/asset-market.md 4.1、4.3 节。
依据:dsc-humanize:docs/design/kernel-and-assets.md 2.8、2.9.1、2.9.2 节。

### 3.4 更新不动用户的编辑,卸载不清用户的内容

- 「包更新保留用户的编辑」不是靠合并实现的,而是靠两者本来就不在一处:包副本是作者的,组合与快照是用户的。
- 更新装成新的版本副本,旧版本保留;同一包的不同版本各存一份,升级不就地覆盖。
- 卸载一个包,删的是该包的副本与记录;用户自写内容与当前使用快照保留,快照里的来源记录仍能回答「这段内容原出自哪个已卸载的包」。
- 合集可发布已下架清单 catalog/removed.json:取不到包时能区分「曾经有、后来下架」与「从来没有」,不删除本地副本。

依据:dsc-humanize:docs/design/asset-market.md 4.2、5.2、5.3、5.4 节。

## 四、现实意义

### 4.1 低门槛贡献:普通用户也能成为创作者

- 做一个资产包只有五步:复制骨架、改元数据、收敛类型目录、按规范填内容、跑校验脚本发布。
- 校验脚本零依赖、不联网:node scripts/validate-asset-package.mjs 即可,退出码明确,错误逐条带字段路径。
- 收录不要求作者提供签名,也不在包内加入签名材料;资产作者在签名体系里「无密钥要求,不签任何东西」。
- 被收录后它仍是普通资产包:用户导入后可以改、可以再导出,没有锁定项,也不因为来自合集而带特权字段。

依据:dsc-humanize-asset-template:README.md「怎么做一个资产包」「如何被合集收录」节。
依据:awesome-dsc-humanize-asset:README.md「三个角色」表(资产作者一行)。

### 4.2 资产可组合、可回退、可撤回

- 可组合:四类内容独立声明来源,一份人设可以配另一包的策略;组合结果记录每一类内容的来源标识与版本,「这次用了哪个包的哪一类」可回答。
- 可回退:版本并存、旧版本保留;快照不随包更新改写,换不换新版由用户重新组合决定。
- 可撤回:下架清单、卸载、来源移除,都有明确的数据边界——撤回影响的是分发,不动用户手里的内容与记录。
- 可追溯:安装记录回答四件事——从哪来、是什么、信不信、用什么。

依据:dsc-humanize:docs/design/kernel-and-assets.md 2.8、2.9.3 节。
依据:dsc-humanize:docs/design/asset-market.md 4.2、4.4、5.4 节。

### 4.3 机制上的三段式:内容侧的分工

- 核心引领:内核与格式规范立住「怎么算」与「算成什么」的边界,类型集合固定,扩展只发生在内核版本里。
- 周边共建:内部合集守默认体验,社区合集开放长尾,格式源头统一,信任域统一。
- 激发体验与自发参与:资产侧用户优化体验——装一个人设、换一套策略,即刻生效;内容创作者的门槛低到「写几个 JSON 文件」。
- 插件与资产的分工让两边的参与成本各自最小化:逻辑贡献者过工程关,内容贡献者过文字关,互不替对方付门槛。

依据:dsc-humanize:docs/design/kernel-and-assets.md 第一节;依据:dsc-humanize:docs/design/asset-market.md 全文。

## 五、为什么值得:从活字到模板的普及路径

雕版印刷的时代,每一本书都是一次重刻,知识复制一次的成本与创作一次几乎一样高;
活字与随后的印刷术普及,把「复制」的成本降到远低于「创作」,知识才第一次有了大众意义上的流通。
资产生态做的是同一件事:把「表达一个想法」的成本压到写 JSON 的水平,
让想法的流通不再以「会写程序」为前提。

这也是在为用户侧积累资产。
人类文明从来不能绝对放弃任何有潜在价值的存在:
一个今天看起来很小的人设、一套标签权重、一段注入文案,都可能在未来某个人那里恰好有用。
门槛每低一分,愿意留下内容的人就多一层;内容多一层,后来者的起点就高一分。
低门槛贡献、可组合复用、可回退可撤回——三者合起来,才构成一个普通用户敢进、进得来、退得出、
留下来的东西还在的生态。

依据:dsc-humanize-asset-template:README.md;依据:dsc-humanize:docs/design/asset-market.md。
